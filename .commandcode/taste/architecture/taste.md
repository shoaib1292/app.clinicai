# architecture
- All ClinicAI apps — dashboard (app.clinicai.pk), landing (clinicai.pk), worker, realtime, and future mobile apps (patient, doctor/receptionist) — must share a single PostgreSQL database and a single Redis instance. No separate databases per app. Confidence: 0.85
- Prefer code-based registries (TypeScript modules mapping IDs to definitions) over database tables for static/config data that is not user-generated. Only introduce a DB table when users need to create/modify their own instances of that entity (e.g., user-created templates). Confidence: 0.75
- Template, Theme, and Brand Color are three separate, independent concepts — never conflate them. Template = block arrangement/layout order. Theme = visual style (CSS variables: colors, fonts, shadows, radius, spacing). Brand Color = single accent override (`--primary`) applied on top of any theme. Clinic picks all three independently. Confidence: 0.85
- Architect UI with composable, reusable blocks/sections from day one — templates should be arrangements of blocks, not monolithic implementations. This keeps the door open for a future block editor without rearchitecting. Confidence: 0.80
- Start with JSON fields on the parent model for flexibility in V1, but always document the migration path to normalized tables for when the data scales. The plan must explicitly state when and how JSON fields will become separate tables. Confidence: 0.75
- Every database query must be tenant-scoped with a clinicId filter — no query should ever lack a tenant WHERE clause. This is a hard rule applied to every query in the codebase, including seemingly global data lookups. Confidence: 0.85
- Analytics/tracking events are an exception to the "JSON first" pattern — tracking data grows too fast for JSON fields; always use a proper events table (`WebsiteAnalyticsEvent`) with worker-based aggregation from day one. JSON counters on the parent model don't scale for event data. Confidence: 0.85
- Clinic websites should be ISR-cached (static regeneration), not dynamically rendered on every request. Use `revalidate` of 60-300 seconds on website pages. Patient portal and booking routes stay dynamic. This keeps websites fast and reduces server load. Confidence: 0.85
- All images on clinic websites (hero, gallery, doctor photos, logos) must go through Cloudflare R2 with server-side Sharp-based transformations (resize to multiple sizes, convert to WebP/AVIF) — never serve raw/unoptimized image URLs on public-facing websites. R2's unlimited egress bandwidth makes it safe for long-term scaling without bandwidth anxiety. Confidence: 0.85
- For smart image placement (face detection, focal-point cropping, auto-enhancement), these were previously handled by Cloudinary AI transforms; with the shift to Cloudflare R2, Sharp handles basic resize/format conversion and any AI-enhanced transforms (face detection, smart cropping) should be handled server-side via a lightweight vision library rather than an external paid API — keep the pipeline self-contained and cost-free. Confidence: 0.70
- SEO must be comprehensive from day one — not just meta title/description. AI should generate: Schema.org JSON-LD (`MedicalClinic`), Open Graph tags, Twitter Cards, `robots.txt`, `sitemap.xml`, and canonical URLs. Every clinic website gets proper structured data for search engines. Confidence: 0.85
- Website builders/editors should include device preview toggles (mobile, tablet, desktop) so clinic owners can see how patients will view their site on different screens. Doctors value this visibility. Confidence: 0.80
- The website block editor should be intentionally constrained: users can inline-edit text, reorder blocks (drag up/down), toggle block visibility on/off, and change the brand color — but NOT build blocks from scratch, use a full WYSIWYG editor, or change the template/theme. The AI picks the template and theme during generation; users only tweak content and order within that fixed structure. This keeps the editor simple enough for non-technical clinic owners. Confidence: 0.80
- Clinic website builder should expose font selection (heading and body fonts) and color palette customization as user-facing theme controls — beyond just a single brand color. This gives clinics genuine visual personalization without needing to understand CSS. Confidence: 0.85
- Clinic website builder must support image upload and management — hero image, logo, and gallery images — so clinics can personalize their websites with their own photos rather than generic placeholders. Confidence: 0.80
- Clinic websites should be visually rich and image-driven, not text-heavy — the user's product vision is for clean, beautiful websites where images carry the visual appeal ("mazy daar websites, blogs banen gy"). This applies to both clinic websites and future blogs/content. Confidence: 0.75
- When a Next.js route exists as a dead stub (returns null, empty, or placeholder) but the real implementation lives at a different canonical path, replace the stub with a `redirect()` to the working page rather than leaving it broken or duplicating code. This keeps URL pathways functional while the canonical implementation stays the single source of truth. Confidence: 0.75
- Cloudflare R2 is the chosen image hosting infrastructure for ClinicAI (over Cloudinary). The founder-level rationale: unlimited egress bandwidth means no scaling cost anxiety, S3-compatible API is standard and portable, a single legitimate account eliminates multi-account ban risk, and pay-as-you-go pricing after the 10 GB free tier is negligible (~$0.015/GB). Confidence: 0.90
- Images uploaded to R2 must be processed through a Sharp-based server-side pipeline before upload: generate multiple sizes (thumbnail ~100px, card ~400px, standard ~800px, large ~1400px, plus original), convert to WebP and AVIF formats, and compress. R2 does not provide on-the-fly transformations like Cloudinary, so this pipeline replaces URL-parameter-based transforms. Confidence: 0.85
- R2's unlimited egress eliminates the need for the multi-account rotation strategy that was required with Cloudinary free-tier bandwidth caps. A single R2 account handles all clinics — no per-clinic account assignment, no usage tracking cron, no 90% cap buffer needed. Confidence: 0.85
- When choosing between infrastructure providers, prioritize long-term safety and sustainability over short-term free-tier perks: a single legitimate account with predictable scaling costs is preferred over multi-account free-tier juggling that carries ban/anxiety risk — even if it requires extra upfront engineering work (e.g., building a Sharp image pipeline instead of using Cloudinary's free transforms). Confidence: 0.80
