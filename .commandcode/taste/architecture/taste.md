# architecture
- All ClinicAI apps — dashboard (app.clinicai.pk), landing (clinicai.pk), worker, realtime, and future mobile apps (patient, doctor/receptionist) — must share a single PostgreSQL database and a single Redis instance. No separate databases per app. Confidence: 0.85
- Prefer code-based registries (TypeScript modules mapping IDs to definitions) over database tables for static/config data that is not user-generated. Only introduce a DB table when users need to create/modify their own instances of that entity (e.g., user-created templates). Confidence: 0.75
- Template, Theme, and Brand Color are three separate, independent concepts — never conflate them. Template = block arrangement/layout order. Theme = visual style (CSS variables: colors, fonts, shadows, radius, spacing). Brand Color = single accent override (`--primary`) applied on top of any theme. Clinic picks all three independently. Confidence: 0.85
- Architect UI with composable, reusable blocks/sections from day one — templates should be arrangements of blocks, not monolithic implementations. This keeps the door open for a future block editor without rearchitecting. Confidence: 0.80
- Start with JSON fields on the parent model for flexibility in V1, but always document the migration path to normalized tables for when the data scales. The plan must explicitly state when and how JSON fields will become separate tables. Confidence: 0.75
- Every database query must be tenant-scoped with a clinicId filter — no query should ever lack a tenant WHERE clause. This is a hard rule applied to every query in the codebase, including seemingly global data lookups. Confidence: 0.85
- Role-based data isolation is a hard requirement: every user role (patient, doctor, receptionist, clinic_admin, platform_admin) must only see data they are authorized for. Patients see only their own appointments/records (scoped by patientId), clinic staff see only their clinic's data (scoped by clinicId), platform staff see cross-clinic analytics. No role should ever be able to access another role's data. Confidence: 0.85
- Analytics/tracking events are an exception to the "JSON first" pattern — tracking data grows too fast for JSON fields; always use a proper events table (`WebsiteAnalyticsEvent`) with worker-based aggregation from day one. JSON counters on the parent model don't scale for event data. Confidence: 0.85
- Clinic websites should be ISR-cached (static regeneration), not dynamically rendered on every request. Use `revalidate` of 60-300 seconds on website pages. Patient portal and booking routes stay dynamic. This keeps websites fast and reduces server load. Confidence: 0.85
- All images on clinic websites (hero, gallery, doctor photos, logos) must go through Cloudflare R2 with server-side Sharp-based transformations (resize to multiple sizes, convert to WebP/AVIF) — never serve raw/unoptimized image URLs on public-facing websites. R2's unlimited egress bandwidth makes it safe for long-term scaling without bandwidth anxiety. Confidence: 0.85
- For smart image placement (face detection, focal-point cropping, auto-enhancement), these were previously handled by Cloudinary AI transforms; with the shift to Cloudflare R2, Sharp handles basic resize/format conversion and any AI-enhanced transforms (face detection, smart cropping) should be handled server-side via a lightweight vision library rather than an external paid API — keep the pipeline self-contained and cost-free. Confidence: 0.70
- SEO must be comprehensive from day one — not just meta title/description. AI should generate: Schema.org JSON-LD (`MedicalClinic`), Open Graph tags, Twitter Cards, `robots.txt`, `sitemap.xml`, and canonical URLs. Every clinic website gets proper structured data for search engines. Confidence: 0.85
- Website builders/editors should include device preview toggles (mobile, tablet, desktop) so clinic owners can see how patients will view their site on different screens. Doctors value this visibility. Confidence: 0.80
- The website block editor should be intentionally constrained: users can inline-edit text, reorder blocks (drag up/down), toggle block visibility on/off, and change the brand color — but NOT build blocks from scratch, use a full WYSIWYG editor, or change the template/theme. The AI picks the template and theme during generation; users only tweak content and order within that fixed structure. This keeps the editor simple enough for non-technical clinic owners. Confidence: 0.80
- Clinic website builder should expose font selection (heading and body fonts) and color palette customization as user-facing theme controls — beyond just a single brand color. This gives clinics genuine visual personalization without needing to understand CSS. Confidence: 0.85
- Clinic website builder must support image upload and management — hero image, logo, and gallery images — so clinics can personalize their websites with their own photos rather than generic placeholders. Confidence: 0.80
- Clinic websites should be visually rich and image-driven, not text-heavy — the user's product vision is for clean, beautiful websites where images carry the visual appeal ("mazy daar websites, blogs banen gy"). This applies to both clinic websites and future blogs/content. Confidence: 0.75
- AI should auto-generate the full visual theme from clinic brand inputs — color palette (3-5 colors: primary, accent, neutral set), font pair, border radius, shadow depth, and animation intensity — rather than requiring clinics to manually configure each property. The Smart Theme Engine makes the same block/template feel unrecognizably different across clinics without manual design effort. Confidence: 0.70
- AI should make content-aware composition decisions when filling a template: analyze the clinic's profile (specialty, city, services count, doctors count) to decide which sections to include/exclude, what the hero should focus on (doctor photo vs. building vs. abstract), whether services display horizontally or vertically, and where to place the CTA for maximum patient acquisition — not just blindly fill all slots. Confidence: 0.70
- When a Next.js route exists as a dead stub (returns null, empty, or placeholder) but the real implementation lives at a different canonical path, replace the stub with a `redirect()` to the working page rather than leaving it broken or duplicating code. This keeps URL pathways functional while the canonical implementation stays the single source of truth. Confidence: 0.75
- Clinic websites should use forgiving URL resolution: when a sub-path like `/doctor/{name}` doesn't match a static route, try to resolve it to a known entity (doctor, service, etc.) and redirect to the appropriate listing page before falling through to 404. A patient sharing or typing a human-readable URL should reach the right content even if the canonical path is different. Implement via a `[slug]/[...path]` catch-all route that does entity lookups and `redirect()` or `notFound()` accordingly. Confidence: 0.70
- Cloudflare R2 is the chosen image hosting infrastructure for ClinicAI (over Cloudinary). The founder-level rationale: unlimited egress bandwidth means no scaling cost anxiety, S3-compatible API is standard and portable, a single legitimate account eliminates multi-account ban risk, and pay-as-you-go pricing after the 10 GB free tier is negligible (~$0.015/GB). Confidence: 0.90
- Images uploaded to R2 must be processed through a Sharp-based server-side pipeline before upload: generate multiple sizes (thumbnail ~100px, card ~400px, standard ~800px, large ~1400px, plus original), convert to WebP and AVIF formats, and compress. R2 does not provide on-the-fly transformations like Cloudinary, so this pipeline replaces URL-parameter-based transforms. Confidence: 0.85
- R2's unlimited egress eliminates the need for the multi-account rotation strategy that was required with Cloudinary free-tier bandwidth caps. A single R2 account handles all clinics — no per-clinic account assignment, no usage tracking cron, no 90% cap buffer needed. Confidence: 0.85
- When choosing between infrastructure providers, prioritize long-term safety and sustainability over short-term free-tier perks: a single legitimate account with predictable scaling costs is preferred over multi-account free-tier juggling that carries ban/anxiety risk — even if it requires extra upfront engineering work (e.g., building a Sharp image pipeline instead of using Cloudinary's free transforms). Confidence: 0.80
- The mobile app functions as a self-hosted SMS gateway: server pushes outgoing SMS requests to the app via persistent WebSocket, the app sends them through the phone's native Android SMS API (`expo-sms` / react-native-sms), and results flow back via the same WebSocket channel. This avoids any third-party SMS provider cost. Each clinic can optionally connect their own phone to send reminders branded from their number; the platform owner's phone handles OTP and platform-level messages. Confidence: 0.80
- Notification channels are strictly partitioned by purpose: WhatsApp (Evolution/Meta API) handles conversational AI replies to patient messages; SMS (via mobile app gateway) handles automated transactional notifications — OTP codes and appointment reminders; Email handles clinic admin and staff authentication/login. Don't conflate these channels. Confidence: 0.80
- When a webhook handler gates on a state-machine status (e.g., `status: 'connected'`) but the expected state-transition event (`connection.update`) may race with data events (`messages.upsert`), implement a self-healing fallback: if no record matches the "ready" status, also try intermediate states (`connecting`, `pairing`), and auto-promote to the ready state when the data event itself proves the dependency is operational. A received message on an instance that's still "connecting" is proof it's connected — don't drop the message waiting for the status event. Confidence: 0.70
- When a Prisma model has optional FK references from child records (e.g., `LLMCallLog.keyId` → `LLMKey`) and `onDelete` is `SET NULL`, null out those references before deleting the parent — call `updateMany({ where: { fkField: id }, data: { fkField: null } })` then `delete({ where: { id } })`. This avoids FK constraint errors from records the Prisma schema allows but the DB engine hasn't yet handled. Confidence: 0.70
- Every API route that saves an outbound message to the database must also actually deliver that message to the external channel (WhatsApp via Evolution/Meta API) in the same request handler — not just persist it and assume a separate worker/queue will pick it up. Both the DB write and the external API call belong in the same route. The DB record alone does not make a message "sent." Confidence: 0.80
- When an in-memory pub/sub store (`store.publish()`) is used to broadcast realtime events but the Socket.io realtime server runs as a separate Node.js process (on its own port, e.g., 3003), every `store.publish()` call MUST be paired with an HTTP POST to the realtime service's `/broadcast` endpoint. The in-memory store can only reach subscribers within the same process — the HTTP bridge is mandatory for cross-process event delivery. This applies to every route that publishes realtime events: webhook handlers, send routes, agent routes, and any future publisher. Consider extracting the dual-publish pattern into a shared helper (`broadcastToRealtime`) rather than duplicating the fetch call. Confidence: 0.80
- Any SSR/SSG page that displays realtime data (chat messages, live feeds, notification streams) must include a client-side refresh mechanism — pair WebSocket/Socket.io subscriptions with polling (`setInterval` + `fetch`) as a reliable fallback. WebSocket transports can fail silently due to cross-process gaps, proxy issues, or network conditions; polling guarantees eventual consistency even when the realtime path is broken. Confidence: 0.80
- When the system checks the health/status of an external integration (Evolution instance, third-party API), the status check should also verify and auto-repair common configuration drift — missing webhook URLs, disabled event subscriptions, stale credentials — rather than just reporting the problem. The status endpoint becomes a self-healing gate: every health check is an opportunity to fix known misconfigurations silently and automatically. Confidence: 0.75

- When passing context through an OAuth redirect flow (e.g., Google sign-in → callback → return to booking page), use a short-lived HTTP-only cookie (`google_auth_return`, `maxAge: 300`) rather than `sessionStorage` or URL query params. `sessionStorage` is domain-scoped and lost during the cross-domain OAuth chain; cookies survive the full redirect round-trip. Clear the cookie after consumption (set `maxAge: 0`). Confidence: 0.75

- When an LLM agent is unresponsive to user intent (ignores questions, repeats itself, keeps defaulting to one workflow), systematically check three things in the system prompt: (a) Does it restrict response length too aggressively? ("Keep replies SHORT, 1-2 lines max" prevents answering substantive questions — prefer "match the user's reply length" or "be concise but complete"), (b) Are maxTokens sufficient for the expected response type? (500 tokens is too small for informative responses like doctor descriptions — bump to 700+), (c) Does the prompt distinguish between different query categories? (info vs booking vs status — a prompt that only handles one domain will fail for adjacent queries even if the model is capable). Confidence: 0.75

- LLM agent system prompts must include explicit handling sections for every query category the agent may receive (doctor info, general clinic info, fees, timing, booking, cancellation, status), with clear distinguishing rules between them — e.g., "Dr Ahmed ka time batao" = info lookup vs "Dr Ahmed se appointment leni hai" = booking action. A single-domain prompt silently fails on adjacent queries because the LLM has no instructions for what to do with them. Confidence: 0.70
- In Next.js 16, avoid `useSearchParams()` in client components — it requires a Suspense boundary that can silently prevent the component from rendering (blank page, no error). Instead, read `searchParams` as a Promise in the server component (`searchParams: Promise<{...}>` → `await searchParams`) and pass the resolved values as props to the client component. This eliminates both the Suspense dependency and the runtime risk of the component tree failing to mount. Confidence: 0.80
- The patient-facing destination platform (portal/mobile app) is a separate repo (`clinicai-patient`, in the Downloads folder) with its own build/deploy cycle — the main ClinicAI repo only contains the patient API routes. The patient portal currently also ships inside the main web app with a mobile-first design, but the standalone app must reach production before the end-to-end "WhatsApp attracts → portal retains" loop is complete. Confidence: 0.75
