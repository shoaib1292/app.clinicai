# code-style
- In Next.js 16 (Webpack), avoid `dynamic(() => ..., { ssr: false })` in Server Components — it's disallowed. Use direct static imports for `'use client'` components instead; the client boundary already handles SSR opt-out. Confidence: 0.80
- Keep computationally simple/deterministic logic (word count, delay formulas, scoring) as pure rule-based functions — never add LLM calls for calculations that can be done with basic math. Confidence: 0.80
- Remove ZAI/Z.AI integration code entirely and use OpenAI as the sole LLM provider — do not keep ZAI as a fallback or disabled option. Confidence: 0.90
- When passing data from a Next.js server component to a client component, never spread full Prisma/decorated objects (`...record`) — explicitly pick only serializable primitive fields. Prisma internals like `_count`, Date objects, and binary fields leak across the server-client boundary and cause serialization errors. Confidence: 0.80
- Remove unused npm dependencies immediately when discovered — dead deps bloat node_modules and slow install/build times. Verify with grep before removing. Confidence: 0.75
- When a feature is labeled "AI" (AI Wizard, AI Generated, etc.), it must call a real LLM — never use string interpolation or template substitution disguised as AI. Fake AI makes features feel disappointing and erodes user trust. Confidence: 0.75
- When the same UI pattern is implemented in multiple places (local component + separate shared component + similar-but-different variants like KpiPill), consolidate into a single canonical shared component with props for variation, then replace all scattered usages. The cleanup must be thorough: remove now-dead local function definitions, strip unused imports (motion, AnimatedCounter, etc.), and simplify prop/config data structures that carried fields only the old local component needed (color, trend strings). Confidence: 0.75
- Use CSS variables for all design tokens in UI components — `--primary`, `--secondary`, `--radius`, `--font`, `--shadow`, and semantic tokens like `--website-bg`, `--website-text`, `--website-surface`, `--website-border`. Never hardcode Tailwind color/text utility classes (e.g., `bg-white`, `text-black`, `bg-gray-100`); always reference CSS variables instead (`bg-[var(--website-bg)]`, `text-[var(--website-text)]`). Tailwind layout utilities (flex, grid, gap, padding) are still fine. This keeps theming and rebranding changes scoped to variable definitions rather than scattered across dozens of component files. Confidence: 0.85
- In Next.js Server Components, never use inline DOM event handlers (`onMouseEnter`, `onMouseLeave`, `onClick`, etc.) — they cause "Event handlers cannot be passed to Client Component props" errors. Use CSS-only alternatives instead: Tailwind `group-hover:` / `hover:` / `focus:` utilities for visual effects, and only convert to a `'use client'` component when JavaScript-driven interactivity is truly necessary. Confidence: 0.75
- When removing the last usage of an imported symbol during refactoring, also remove its import statement — don't leave dead imports behind. Stale imports can cause Next.js chunk/module-factory errors even when the symbol isn't referenced in JSX, especially with lazy-loaded icon libraries like lucide-react. Confidence: 0.80
- Never render `<link rel="stylesheet">` or similar head/resource tags inside client components in Next.js 16 + React 19 — client-rendered `<link>` tags go through React DOM's `useInsertionEffect` path and crash under Turbopack with "Cannot read properties of null (reading 'useInsertionEffect')". Render font/resource links in the server layout instead (with `precedence="default"`), where Next.js handles them natively. Confidence: 0.75
- When removing a feature during refactoring, also clean up the associated `useState` declarations AND all their setter calls — not just the JSX that rendered them. Dead state variables don't cause build errors (unlike dead imports) but silently bloat the component and cause confusion. This extends the "remove unused imports" discipline to React state management. Confidence: 0.70
- When implementing `contentEditable` in React/Next.js components with SSR, follow this pattern: (a) use a **single unified render path** — never branch between edit and non-edit views (no `if (!isEditMode) return <X>`) because different DOM trees cause hydration mismatches beyond what `suppressHydrationWarning` can fix, (b) render `{value}` as JSX children (not zero children) so server and client produce structurally identical HTML — the Ref + `.textContent` sync handles keeping the DOM in sync post-mount, (c) initialize edit mode as `useState(false)` and set it in `useEffect` via `URLSearchParams` — both server and client render the non-edit state first, (d) toggle only `contentEditable` and `onBlur` props (not the element structure itself), (e) use a ref to sync `.textContent` when the external value changes and the user is not actively focused in the element, (f) use CSS pseudo-classes (`focus:ring`, `focus:bg`) for the visual editing ring — never React state changes (`onFocus`/`onClick` → `setEditing(true)`) because state-driven re-renders destroy the browser's contentEditable cursor, (g) only use React state for the `saving` boolean (to disable contentEditable during API calls). `dangerouslySetInnerHTML` also creates problems — React re-applies it on re-render, blowing away user edits. Confidence: 0.90
- Never use `typeof window !== 'undefined'` or `new URLSearchParams(window.location.search)` directly in a component's render path to branch between server and client output — it causes hydration mismatches because server and client produce different DOM trees. `suppressHydrationWarning` only masks attribute-level differences, not structural tree differences. Instead, initialize with `useState(false)` (the server-safe value) and set the client value in `useEffect`, so both sides render the same initial tree. Confidence: 0.85
- When working with dates in database queries (Prisma/SQL), always use UTC-based date construction (`new Date(Date.UTC(y, m, d))`) and UTC-based range queries (`gte: new Date(Date.UTC(y, m, d)), lt: new Date(Date.UTC(y, m, d+1))`), not local-time `new Date(y, m, d)` or equality queries on a `Date` column. Local-time date construction creates timezone mismatches between stored and queried dates (e.g., Pakistan UTC+5 stores as UTC-5h), causing queries to return empty even when matching records exist. Also use `getUTC*()` methods in date comparison helpers (`sameDay`, etc.) for the same reason. Confidence: 0.85

- When a Next.js page renders correctly during SSR but silently crashes/breaks after client-side refresh (components disappearing, buttons missing, no visible error), suspect a TypeScript interface mismatch: the client-side `interface` declares a Prisma-shaped nested object (e.g., `_count: { callLogs }`) but the API actually returns a flat field (e.g., `callCount`). Accessing a nested property on a flat object silently fails — no crash, just a dead component tree. Fix both layers: (a) align the interface with what the API actually returns (flat `callCount?: number`), and (b) use nullish coalescing (`k.callCount ?? 0`) for display safety. Also check the server component's data-fetching to ensure it's passing the correct shape to the client. Confidence: 0.65

- When building LLM system prompts inside JavaScript template literals (backtick strings), any `${...}` that is meant as literal text for the LLM to interpret must be escaped as `\${...}`. JavaScript template literals interpolate `${expr}` as code — if the expression references a variable that doesn't exist in scope, the entire function crashes with a `ReferenceError`. This happened when `${alternativeSlot.startTime}` and `${alternativeSlot.tokenNo}` were placed unescaped inside `buildSystemPrompt`'s template literal, causing every agent call to fail silently. The fix: `\${alternativeSlot.startTime}` and `\${alternativeSlot.tokenNo}` so the dollar-brace passes through as-is to the LLM. Confidence: 0.85
- When using framer-motion `motion.div` with `variants` for fade-in/entrance animations, always include `opacity: 1` in the `visible` variant — not just a `transition` configuration. A `visible` variant with only `transition` (and no explicit opacity) leaves elements at their default/hidden opacity, making them exist in the DOM but appear invisible (white elements blending into a white background). This is a common bug when `hidden` sets `opacity: 0` but `visible` only configures timing without restoring opacity. Confidence: 0.70
