# ui
- The dashboard app uses shadcn/ui as its UI component library — components should follow shadcn/ui conventions, not raw or custom-styled components. Confidence: 0.80
- Auth/marketing pages (login, signup) should share a consistent split-screen layout: image slider on the left, form on the right, with framer-motion staggered spring entrance animations on form elements. When designing a new auth page, replicate the pattern from existing pages rather than inventing a different layout. Confidence: 0.75
- Imagery theme should match page purpose: login/trust-building pages use familiar clinic/healthcare photos, while signup/onboarding pages use AI/tech imagery to evoke excitement about adopting AI. Don't use the same stock photo category across all pages — tailor the visual story to what the user should feel at that step. Confidence: 0.70
- ClinicAI logo/branding should appear consistently site-wide and link to landing page, except in dashboard. Confidence: 0.75
- Dashboard sidebar should scroll independently from main content area, not stretch full page length. Confidence: 0.75
- All platform admin sub-pages must be wrapped in `<DashboardShell>` — missing the wrapper causes the sidebar to disappear. Use dynamic `userType={session.type as 'platform_admin' | 'platform_staff'}` rather than hardcoding `"platform_admin"`, so platform_staff users can also access these pages. Confidence: 0.80
- Public-facing clinic websites should use shadcn/ui primitives (Button, Card, Badge, Avatar, Carousel, Separator, Sheet) combined with Aceternity UI-style animations (framer-motion) for a modern, polished, and readable patient experience. Confidence: 0.85
- Dashboard sidebar/navigation must be organized by usage frequency: daily-use items go in the main sidebar tabs, while occasional or one-time-use items belong lower in the sidebar or nested under Settings. The user explicitly wants this frequency-based hierarchy — not arbitrary grouping or aesthetic symmetry. Confidence: 0.85
- Branding/theme configuration UIs (color pickers, font selectors, style editors) must include a working live preview so changes are visible in real-time — configuration tools without live preview feel broken and incomplete. Confidence: 0.80
- Builder/editor experiences (website builder, content editors, any creative/building workflow) should use an immersive full-viewport layout that feels like a dedicated standalone page: the dashboard sidebar, topbar, AND footer disappear entirely, and the builder's own tab navigation (e.g., Quick Setup | AI Wizard | Edit Blocks) must also be hidden — not just the sidebar. Only the editing tools (exit/back, save/publish, device toggle, blocks/text-editing toggles) plus the large preview canvas remain. The user explicitly rejected a version that kept the tabs after expand: "no sidebar, no tabs, aur na koi aur features — sirf website builder/editing tools hon sirf", GHL-style. Confidence: 0.85
- The immersive/full-page builder mode should be the DEFAULT state when opening the editor — the user expects the full-page experience immediately, without having to click a Maximize/expand button first. The user complained "kuch bhi nahi badla" when the builder still opened in the normal dashboard layout. Confidence: 0.8
- Top bar/toolbar controls in editors and builders must never overlap the page title or heading — layout them in normal flex flow (inline with the other buttons), never absolutely positioned over text. The user flagged an Exit button overlapping the "Website Builder" title as a broken UI ("UI kharab") and expects a clean arrangement; they are fine with either centering the title or any layout that simply looks better. Confidence: 0.75
- Branding must be consistent across ALL patient-facing surfaces: whatever brand color and fonts a clinic sets in the website builder must also appear on the patient portal (and any other patient-facing surface) so the patient never feels they've landed in a different app. The website builder's brand settings should be the source of truth; portal-specific branding fields are only fallbacks. The user explicitly requested this ("jo user brand color use kary wahi usky patient portal pr bhi aaye... user ko ya na lagy k wo kisi aur app pr aa gya hai"). Confidence: 0.85
- Patient-facing surfaces (patient portal, booking flow) should feel like a native app, not a website — typography (fonts, sizes) should be chosen for an app-like feel and easy readability. The clinic's selected body/heading fonts should apply across the whole portal, not just isolated elements. The user asked for this explicitly ("font not change because app like feel not web like feel aur read karny me aasan"). Confidence: 0.75
- Prefers focused, single-purpose dialogs over monolithic multi-section dialogs. When a dialog becomes "bulky" with unrelated sections (e.g., profile settings mixed with schedule editor), split them into separate popups, each with its own dedicated trigger button that includes a relevant icon (e.g., CalendarDays for schedule). A single "Edit" button should not carry everything. Confidence: 0.85
- Dashboard edit/create dialogs must open as constrained popups, NOT full-screen pages — use `max-w-md sm:max-w-md` on `DialogContent`. The user explicitly rejected full-screen dialogs: "full screen pr khul jata hai. popup UI k sath open ho to zyada behtar with scroll". **Preferred approach (simplest, most reliable):** `max-w-md sm:max-w-md max-h-[80vh] overflow-y-auto` on `DialogContent` with standard shadcn `DialogHeader` and `DialogFooter` — the entire dialog scrolls as one unit, no custom flex/grid fighting with Radix internals. This avoids div-structure errors and broken footer visibility that plague the override approaches. **Only if footer must be pinned while content scrolls, try:** Grid override with inline `style={{ gridTemplateRows: 'auto minmax(0, 1fr) auto' }}` or Flex override with inline `style={{ display: 'flex', flexDirection: 'column', maxHeight: '85vh' }}`. However, both overrides are fragile — they require precise inner div nesting (header `shrink-0`, content `flex-1 overflow-y-auto min-h-0`, footer `shrink-0`) and often cause cut-off buttons or JSX structure errors. When they fail repeatedly, give up and use the simple `overflow-y-auto` approach above; the user cares more about functional buttons than pinned footers. Also note: shadcn's `DialogContent` has a default `sm:max-w-lg`, so both `max-w-md` AND `sm:max-w-md` are needed to properly constrain on desktop. Confidence: 0.92
