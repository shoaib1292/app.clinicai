# workflow
- Before any destructive action (deleting files, removing folders, stripping code), first produce a documented plan and get explicit approval. Never delete without confirmation, even during cleanup/audit tasks. Confidence: 0.70
- When the user asks for a feature or change, first explore the relevant existing codebase thoroughly (current auth flows, data models, session handling, existing but unused infrastructure), then present a structured analysis with a clear recommended strategy and ask for confirmation — before writing any implementation code. Confidence: 0.75
- When the user asks whether a third-party service is easy to integrate ("kia tum X integrate kr do gy?", "proper add karna aasan hai?"), treat it as a feasibility question: inspect their actual codebase (schema, booking flow, portal, dashboard, auth patterns) and answer with a concrete effort estimate — days/sessions, files touched, task breakdown, and honest risk points (e.g., TURN/NAT for WebRTC) — plus an explicit step-by-step implementation offer. "Proper" integration means production-ready (webhooks, billing, edge cases), not a demo. Confidence: 0.6
- When the user asks a founder-level technology choice question ("X vs Y, kia best hai as a founder"), give a definitive, well-reasoned recommendation with concrete reasoning — not a neutral feature comparison. The user wants the assistant to take a stance, justify it with data (pricing, limits, trade-offs), and provide a phased strategy for when to revisit the choice at scale. The user often frames these as "long term for ClinicAI" — so factor scalability, upgrade paths, and open-source/self-host escape hatches into the recommendation, not just today's cheapest option. Confidence: 0.75
- When integrating a new third-party service or API (e.g., Daily.co, Agora), thoroughly read the external documentation first before writing any implementation code — don't guess or rely on training knowledge alone. Confidence: 0.85
- When consolidating multiple duplicate/overlapping documents (analysis reports, plans), create a single merged reference .md file first before removing the originals. Confidence: 0.65
- Current deployment priority: web app (app.clinicai.pk) and landing page (clinicai.pk) first, mobile apps deferred until web is live. Focus on testing, polishing, and deploying the web experience within a tight 2-3 day timeline. Confidence: 0.70
- Prefer managing LLM API keys through the Platform Admin → LLM Keys UI rather than environment variables or local config files. Confidence: 0.80
- When a code fix doesn't resolve an issue, verify at runtime by checking server status, logs, DB state, and external API connectivity — don't just re-read code or assume the fix worked. Confidence: 0.85
- When the user reports "nothing changed" after UI edits (or reports a UI bug that the current code cannot possibly produce, e.g., an old button/title overlap), the usual culprit is stale code being served — either browser cache on the tunneled URL (app.clinicai.pk) or a dev server that was started BEFORE the edits and keeps serving the old compiled bundle. Verify by grepping the source for the reported old strings, searching .next chunks for the new strings, and checking the dev server's start time vs. edit time; only then tell the user to hard refresh (Ctrl+Shift+R), use incognito, or restart the dev server — rather than assuming the code is wrong and redoing it. Confidence: 0.8
- Check actual runtime configuration of external services (e.g., webhook settings on Evolution instances) via API calls rather than only inspecting code — the real root cause may be a runtime config issue, not a code bug. Confidence: 0.80
- Test external API endpoint behavior with real HTTP requests (e.g., PowerShell Invoke-WebRequest) before implementing fixes, to verify the correct request format and parameters empirically rather than guessing from code alone. Confidence: 0.75
- When the AI agent stops responding to messages, systematically debug by: checking if the server is running (netstat), testing the webhook endpoint with a real HTTP request, checking DB for message state, checking server logs, identifying stale server processes, killing old PIDs, restarting the server, waiting for boot, and re-testing. Confidence: 0.80
- When STT/transcription fails or returns an unsupported language, the AI agent should respond in Urdu asking the user to speak in Urdu or send a text message, rather than showing a technical error or generic failure. Confidence: 0.85
- When restarting the dev server, kill the old process by PID first to ensure stale code is cleared, then start fresh in background and wait for full Next.js boot before sending test requests. Confidence: 0.75
- When running Next.js dev on Windows, Turbopack native bindings are not available at all (win32/x64) — always use `next dev` without `--turbo` (which defaults to Webpack). This is not just a background-job issue; Turbopack is fundamentally unsupported on this platform. Confidence: 0.90
- When a command or tool hangs/stalls (e.g., shell_command timing out or being repeatedly interrupted), immediately pivot to an alternative approach (PowerShell, different tool, direct API call) rather than waiting or retrying the same method. The user values fast, unstuck execution and gets frustrated by visible delays. Confidence: 0.85
- When building a new mobile app, build the complete frontend/UI first with mock/static data before wiring any backend — so the user can visually test the app on their device (Expo Go) early, without waiting for API integration. Confidence: 0.85
- When the user asks forward-looking questions about long-term workflow, capabilities, or roadmap ("aagy kia karon ga", "kis had tak help karo gy"), provide a transparent, structured breakdown covering: (a) daily operational workflow after go-live, (b) what the assistant can help build (with concrete feature categories), and (c) what the assistant explicitly cannot do (with reasons why). Be honest about limitations rather than over-promising — the user values knowing boundaries upfront. Confidence: 0.75
- Skills installed via `npx -y skills add --agent claude-code` land in `.claude/skills/` by default, but Command Code only detects skills from `.commandcode/skills/`. After installing skills for Claude Code, also copy them to `.commandcode/skills/` (on Windows use `xcopy /E /I /Y`) so Command Code can use them too. The user expects skills to work in both environments. Confidence: 0.75
- After installing new skills, always provide a brief table explaining how to use each skill (e.g., `/skill-name` for what purpose) — the user wants practical usage guidance, not just installation confirmation. Confidence: 0.70
- When the user asks for a plan ("short sa plan btao"), keep plans concise and high-level with only the key structure — not exhaustive multi-page documents. The user prefers a quick overview they can scan and approve. Confidence: 0.70
- When delivering code (especially mobile apps), self-verify by actually running the app, fixing all runtime errors, and only report "done" when it genuinely starts without errors. Never hand off untested work — the user gets frustrated when told something works only to hit errors immediately on their end. Confidence: 0.90
- When killing processes after verification, be surgical — kill only the specific command/process that was started for testing (e.g., just the Expo dev server), not other running services or background tasks. Confidence: 0.70
- When the assistant gets stuck on mobile app development (repeated errors, dependency issues, runtime crashes), pivot to a handoff: document the backend API in a comprehensive `.md` reference file (endpoints, request/response JSON, auth flow, screen-to-API mapping, design rules), and let the user build the frontend in Google AI Studio — they will come back for backend integration. The user views Google AI Studio as their reliable mobile frontend builder and prefers splitting work this way rather than having the assistant keep fighting mobile tooling issues. Confidence: 0.85
- Once a handoff/reference document has been created for another tool (e.g., a `.md` file for Google AI Studio), keep it stable and communicate supplementary information directly in chat — don't edit the handoff document. The user treats these as clean artifacts for a specific recipient and doesn't want them polluted with follow-up additions. Confidence: 0.65
- When the user reports multiple errors at once, diagnose all of them in parallel first (simultaneous file reads, grep searches, schema checks), create a structured fix plan (todo list), apply all fixes together, then verify — rather than fixing errors one at a time sequentially. The user expects the full error surface to be resolved in a single efficient pass. Confidence: 0.80
- After making code edits, provide a transparent summary of exactly which files were touched (e.g., `git diff --stat HEAD`) so the user can verify their existing uncommitted work wasn't disrupted. The user often has significant uncommitted changes and gets anxious when they think work may have been overwritten. Confidence: 0.65
- Stay focused on the current feature/task until it is genuinely complete — do not proactively pivot to a new topic or workstream (e.g., reading design docs, activating skills for unrelated work) while active development is still in progress. The user will explicitly direct the next priority when ready. Confidence: 0.85
- When development tools, system packages, or utilities (Python, CLIs, SDKs) are needed for the task, install them without asking for permission — the user expects the assistant to be self-sufficient for tooling setup. Only consult on substantive architecture/product decisions, not tool installation. Confidence: 0.75
- When the user says "kaam shuru karo step by step", implement in clearly communicated phases with todo tracking — don't try to do everything in one monolithic pass. The user wants visible, incremental progress they can follow. Confidence: 0.80
- Stay in planning mode — iterate on the plan document only — until the user explicitly says to start implementing. During planning, update the plan file based on feedback but do NOT write any implementation code. The user will give an explicit signal (e.g., "kaam shuru karo") when ready. Confidence: 0.85
- When the user references a design file with `@filename.md` notation (e.g., `@block.md`), that file is the creative brief — it contains specific visual concepts and design mockups that should be faithfully reproduced in implementation, not loosely interpreted. Search for these files in the project root and treat them as first-class design specs alongside the plan document. Confidence: 0.75
- When fixing a structural/layout issue on a page (missing sidebar, broken shell, wrong parent wrapper), first read an existing working page of the same category/section to see the correct structural pattern, then apply it to the broken page — don't guess the wrapper/props from memory. The codebase has consistent patterns (e.g., DashboardShell wrapping, session→redirect flow) that should be copied verbatim from sibling pages. Confidence: 0.80
- When a server component already has session data (clinicId, userId, userName) from `getSession()`, pass it as props to child client components rather than having the client fetch `/api/auth/me` again. This avoids redundant network round-trips and keeps the data flow unidirectional. Confidence: 0.75
- When a Next.js route 404s despite the route file existing at the correct path, check the middleware/proxy layer (`proxy.ts`/`middleware.ts`) for incorrect rewrites before debugging route registration or file structure. Domain-based middleware that rewrites all traffic can silently redirect valid routes to non-existent paths (e.g., `/p/al-shifa` → `/website/al-shifa/p/al-shifa`). Confidence: 0.75
- Before adding directories to tsconfig.json `exclude`, verify no source files import from those directories — excluding an imported directory causes hard-to-diagnose module resolution errors. Check with grep rather than assuming directories are isolated. Confidence: 0.70
- During active development/testing phases, hardcode auth/security values (OTPs, verification codes, magic links) to simple test constants so testing is frictionless — the real logic will be restored before production. Mark temporary code with `// TEMP:` comments so it's easy to find and revert later. Confidence: 0.75
- When the user reports a feature isn't working at a high level ("booking nahi ho rahi", "data nahi aata"), explore the entire feature flow end-to-end first — all related pages, all API routes, and all data models — before diagnosing or fixing. The root cause is often spread across multiple files and a narrow investigation misses the full picture. Confidence: 0.75
- When a file has accumulated multiple bugs or structural issues (JSX mismatches, wrong Prisma fields, bad function signatures), especially after several incremental `edit_file` calls have compounded errors, prefer a clean wholesale rewrite (via `write_file` or a single large `edit_file`) over further incremental fixes. Use `edit_file` only for single isolated fixes. Repeated small edits on a broken structure risk accumulating more errors and frustrating the user. Confidence: 0.80
- When the user reports a feature still isn't working after a previous fix was claimed "done," start by re-reading the current file state — the previous work may have been incomplete (e.g., types/helpers added but never wired to UI state or save logic) rather than broken by subsequent changes. Don't assume the earlier work was complete just because it was marked as done. Confidence: 0.75
- After writing or rewriting API route files, always run `npx tsc --noEmit` filtered for the changed files to catch type errors before reporting completion — don't assume rewritten code is type-correct just because the logic looks right. Catching Prisma field mismatches and function signature errors immediately saves back-and-forth. Confidence: 0.75
- When Next.js throws a "module factory is not available" error (especially for lazy-loaded icon/component libraries like lucide-react), clear `.next` cache directory and check for dead imports — the stale chunk cache can reference modules that are no longer used, and the error persists until both the cache is cleared AND the unused imports are removed. Confidence: 0.75
- Prefers quality over quantity: individual features must be polished with proper design feel rather than mass-producing many functional-but-bland blocks. When implementing from a design spec file (like block.md), first discuss each component's visual flow and design intent collaboratively before writing any code — never skip the design conversation and jump straight to functional implementation. The user values craftsmanship over throughput. Confidence: 0.85
- When reorganizing sidebar/navigation, never remove existing links — the goal of reorganization is to move, regroup, and reprioritize items, not to delete them. Removing nav entries breaks existing flows and makes features inaccessible (the user calls this "ghaib karna" — making things disappear). After any navigation restructure, verify every previously-accessible page is still reachable from the sidebar. Confidence: 0.85
- Before recommending or sizing any self-hosted service (LiveKit, video SFUs, mail servers), read the official self-hosting/deployment documentation for sizing guidance (CPU, RAM, bandwidth per participant/concurrent call) and ground the capacity math in those numbers rather than estimating from general knowledge. Confidence: 0.70
- When a UI crash is caused by missing/undefined data from an API response, apply a two-layer fix: (a) add optional chaining/nullish coalescing at the call site for immediate crash prevention, then (b) fix the API query (Prisma include/select) to return the missing data. Don't stop at just the defensive frontend patch — the proper fix is at the data layer. Confidence: 0.75
- When the user says "continue" mid-investigation, they're signaling to keep going with the current workstream — don't wait for more input or ask clarifying questions. Just proceed with whatever the next logical step is. Confidence: 0.60
- Never run a command that would kill the assistant's own Node.js process (e.g., `Get-Process -Name "node" | Stop-Process -Force`). When such a command is needed, give it to the user to run manually in their own terminal instead. The user has explicitly complained about this pattern ("tum khud ko hi band kar dete ho"). Confidence: 0.80
